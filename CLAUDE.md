# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Run in development mode (default profile "dev", port 8080)
./mvnw

# Run unit + browserless view tests
./mvnw test

# Build production JAR (no -Pproduction needed in Vaadin 25: vaadin-dev is optional)
./mvnw clean package

# Run integration tests
./mvnw -Pit

# Build and copy JAR to release/ dir
./build.sh

# Deploy to remote server (cloud@cloud.attocchi.it via rsync); server runs deploy/start.sh
./deploy.sh
```

Claude Code project commands (`.claude/commands/`): `/build` runs `build.sh`, `/deploy-test` and `/deploy` run `deploy-test.sh` / `deploy.sh` (only the user can start them; `/deploy` asks for confirmation unless called with `si`). On the server pm2 watches the folder and restarts the app when the JAR changes.

## Architecture

**Spring Boot 4.1.1 + Vaadin 25.3.1** (Flow, server-side Java UI; Vaadin 25.3 requires Spring Boot ≥ 4.1) for managing music courses. No separate frontend framework.
Use the Vaadin MCP server (`.mcp.json`) to check Vaadin 25.3 APIs before writing UI code — many older APIs are deprecated or removed.

### Roles and access

Five roles: `ADMIN` (full management), `SEGRETERIA` (courses, participants and lesson times, allievi (students); read-only lists of teachers and parents; no deletions, no user management), `INSEGNANTE` (teacher lessons), `ALLIEVO` (own courses; called *Studente* until 2026-10-11), `GENITORE` (children's courses). Views shared by admin and segreteria use `@RolesAllowed({"ADMIN", "SEGRETERIA"})` and hide admin-only actions (e.g. Elimina) with `securityService.hasRole("ADMIN")`.
- Views are protected with `@RolesAllowed` / `@PermitAll`; `MainLayout` itself is `@PermitAll` (layouts are access-checked too).
- The side menu is built from `@Menu` annotations via `MenuConfiguration.getMenuEntries()`, which already filters by access — don't add manual role checks to the menu.
- `SecurityService` wraps Vaadin's `AuthenticationContext` (`getUsername()`, `hasRole()`, `logout()`).
- `HomeView` is the role-based dashboard (`DashboardService` counts, one section of Vaadin `Card`s per role of the user). Right after the greeting, "Prossima lezione"/"Prossime lezioni": per active course the first lesson still to do from today (`DashboardService.prossimeLezioniInsegnante` / `prossimeLezioniAllievo` / `prossimeLezioniDeiFigli`, called per role; allievo/genitore with the participant's `Iscrizione.orarioLezione`, genitore one per child and course), "Oggi"/"Domani" badge, clickable `Card` (`role=button`, click via `ComponentUtil.addListener(ClickEvent)` and Enter; in tests `ComponentUtil.fireEvent(card, new ClickEvent<>(card))`): the teacher goes to the attendance register (`DettaglioLezioneDialog.apriPresenze` → Le Mie Lezioni `?lezione=ID`), allievi/genitori get the read-only `views/DettaglioLezioneDialog` (also used by the Calendario). A teacher without hourly rate (`BilancioService.haTariffa` false, forfait or not) gets an "Ore donate" card: `BilancioService.oreDonate` = minutes of completed lessons on active courses (same formula as the costs: expected students incl. absent × duration, lessons the teacher attended), "su X previste" = all lessons except not held, shown with `Formati.durata` ("12 h 30 min"). Seeded lessons are in 2024: tests add future lessons with `LezioneService.aggiungi` and remove them. A genitore's "I miei figli" section also has "Pagato" and "Da pagare" for all children on active courses (`PagamentoService.situazioneDeiFigli`). The "Riepilogo generale" has Corsi, Allievi, "Iscritti ai corsi attivi" (enrolments, a student counts once per course), Genitori, Insegnanti. The "Pagamenti dei corsi attivi" section also shows, per course, "Costo insegnanti" (`BilancioService.costiPrevistiPerCorso()`, "Senza tariffa" if missing, no annual forfait) and "Margine" = fees due − cost with an Attivo/Perdita badge, plus the two total cards (courses without a tariff excluded). Admin/segreteria also see "Gruppi dei corsi attivi" (`DashboardService.riepilogoGruppi()`: cards + one row per group with its participants); a teacher sees the same table for their own courses (`gruppiDellInsegnante`) only when they have groups. Browserless tests start on the Home route: navigate away and back to rebuild it after changing data. Start page: on the first navigation of the session (after login) `MainLayout.beforeEnter` forwards a user whose only role is INSEGNANTE and who has a single active course from Home to `LezioniInsegnanteView`. So in tests with insegnante1/insegnante2 that view is already open at start: reopen it via Home (`apriLezioni()` in `ViewAccessTest`).

### Package layout

```
it.attocchi/
├── entity/         JPA entities (id-based equals/hashCode)
├── repository/     Spring Data JPA repositories — used only by services (and DataInitializer)
├── service/        Business services, @Transactional(readOnly = true) by default
├── security/       SecurityConfig, SecurityService, UserDetailsServiceImpl
├── views/          Vaadin views by role (admin/, insegnante/, allievo/, genitore/) — depend on services only
├── Application.java       AppShellConfigurator: loads Aura theme + styles.css via @StyleSheet
└── DataInitializer.java   Seeds test data (dev profile only)
```

### Profiles and database

- `application.properties`: shared config; `spring.profiles.default=dev`.
- **dev** (`application-dev.properties`): H2 in-memory, `create-drop`, H2 console at `/h2-console`, `DataInitializer` seeds users (admin/admin, segreteria/segreteria, insegnante1/insegnante1, …).
- **prod** (`application-prod.properties`): MySQL, credentials from env vars `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`; `ddl-auto=update` (Flyway still to do). Started with `--spring.profiles.active=prod`. Schema changes that `update` can't apply (renamed tables/columns, changed stored values such as role names) need a manual SQL script in `docs/migrazioni/AAAA-MM-GG-<argomento>.sql`, to be run on MySQL before deploying.

### Key design patterns

- `spring.jpa.open-in-view=false`: everything a view displays must be loaded by the service (use `JOIN FETCH` queries for lazy collections). Browserless tests in `ViewAccessTest` catch `LazyInitializationException`.
- Theme is **Aura**: use unprefixed variants (`ButtonVariant.PRIMARY`), not `LUMO_*` or `LumoUtility`.
- Styling uses **Tailwind CSS** (experimental Vaadin feature flag `tailwindCss` in `src/main/resources/vaadin-featureflags.properties`, Tailwind 4 via Vite, no preflight): layout and element styles are utility classes added with `addClassNames("…")` in Java; combinations used in several places are constants in `views/Stili` (`TESTO_SECONDARIO`, `TITOLO_SEZIONE`, `RIEPILOGO_PAGAMENTI`, `LOGO`). Write class names literally in the source (the compiler scans `src/`; never build them at runtime). Colors, font sizes/weights and radii come from Aura tokens (`text-(--vaadin-text-color-secondary)`, `text-(length:--aura-font-size-s)`, `font-(--aura-font-weight-medium)`), Tailwind's scale for spacing and layout; `sm:` = 640px = `ViewSupport.MOBILE_BREAKPOINT`, `dark:` = prefers-color-scheme. Two utilities for the same property don't override each other by class order (the generated CSS order wins): choose one in Java instead. `styles.css` keeps only rules on Vaadin component internals (`::part`, `vaadin-grid-cell-content`). Layout too is Tailwind: `VerticalLayout`/`HorizontalLayout` stay as components but are configured only with classes, never with their Java APIs (inline styles set by `setWidth`/`setFlexGrow`/alignment would beat the classes): `setSizeFull` → `size-full`, `setWidthFull` → `w-full`, `setPadding(false)` → `p-0`, `setSpacing(false)` → `gap-0`, `setWrap(true)` → `flex-wrap`, alignment → `items-center`/`items-baseline`/`justify-center`, `expand(c)` → `c.addClassNames("grow")`, fixed widths → `w-40`… (`VerticalLayout` already has width 100% and padding+spacing by default; classes override the theme defaults). Only Grid column widths/flex and Dialog widths stay as API. `FormLayout` is kept as is.
- The Insegnanti and Genitori lists show the `Insegnante`/`Genitore` records, not users with the role. Gestione Utenti saves through `SchedeRuoliService.salvaUtente`, which creates the missing record for the INSEGNANTE, GENITORE and ALLIEVO roles (personal data copied from another record of the same user via `Anagrafica.copia`); `SchedeRuoliIniziali` does the same at startup. Removing a role keeps the record. Admin can delete a genitore or insegnante record without deleting the user ("Elimina" in Genitori/Insegnanti → `GenitoreService.elimina`: children left without parent; `InsegnanteService.elimina`: refused if the teacher has courses, lessons or reimbursements); the user loses that role. Deleting a user from Gestione Utenti goes through `SchedeRuoliService.verificaEliminazione`/`eliminaUtente` (confirmation listing the records deleted with the user; refused with a reason if a record has links — allievo with payments, enrolments or attendances, insegnante with courses/lessons/reimbursements — or for one's own user); `UserService.delete` alone fails on the foreign keys. Gestione Utenti flags inconsistencies (`SchedeRuoliService.incongruenze()`: role without record, record without role) with warning badges in the "Schede" column, a "Solo incongruenze" filter and a "Crea schede mancanti" button.
- Passwords are only set via `UserService.save(user, rawPassword)` (encoded there; null/blank keeps the existing one).
- People: `Allievo`, `Genitore`, `Insegnante` implement `Anagrafica` (codice fiscale, nascita, embedded `Indirizzo` mapped on the existing columns `indirizzo`/`cap`/`citta` + `provincia`); `getIndirizzo()` is never null. Edit forms reuse `views/UtenteFields` (user + contacts) and `views/AnagraficaFields` (validates `CodiceFiscale` and CAP/provincia); admin/segreteria save user + person in one transaction (`XxxService.salva(person, user, password)`), self-service profiles (`ProfiloView`, children in `FigliView`) go through service methods that copy only the allowed fields. The genitore of an allievo is optional (adult students): documents and emails then go to the allievo, and the allievo manages their own payments like a parent of themselves (`AllievoService.gestisceDaSe`): "Pagamenti" (`allievo/MieiPagamentiView`, menu item shown by `MainLayout` only to allievi without genitore, built at login), their own documents in "Documenti" (receipts, confirmations and the yearly riepilogo, `DocumentiService.riepilogoAllievoPer`), Pagato/Da pagare cards in the dashboard (`PagamentoService.situazionePropria`) and a "Pagamento" status column in I Miei Corsi. An allievo without any address field shows the parent's one with "(del genitore)" (`Formati.indirizzo`), never copied. An allievo's codice fiscale and data di nascita are optional (MySQL columns made nullable by `docs/migrazioni/2026-10-13-allievi-dati-facoltativi.sql`) but required for receipts and confirmations: `Allievo.getDatiMancantiPerDocumenti()`, `DocumentiService.avvisoDatiMancanti(allievo)` (documents and emails are refused, the bulk send skips and counts them, the PDF button in Documenti shows the warning instead of the PDF, "Dati mancanti" badge in Gestione Allievi and Documenti). A new allievo, genitore or insegnante without username (`UtenteFields(user, userService, true)`) gets one generated by `UserService.usernameLibero(nome, cognome)`, a random password and a disabled user (`UserService.accessoGeneratoSeManca`); access is granted later in Gestione Utenti ("Attivo"). The genitore dialog also sets the children (`MultiSelectComboBox` "Figli" → `GenitoreService.salvaConFigli`: chosen allievi move to this parent, removed ones are left without one).
- Payments: `Iscrizione.quotaPersonalizzata` (null = `Corso.costoTotale`) and `Pagamento` rates; computed by `PagamentoService` (`Situazione`, `RiepilogoPagamenti`, `Ricevuta`), allowed also on inactive courses. Status badge/colour via `views/StatoPagamentoUI`. Receipts are only in Documenti (see below). Every PDF button is a `views/MenuPdf` (a `MenuBar` drop-down with "Anteprima in una nuova scheda" = inline link with target `_blank`, and "Scarica PDF"; links, not server actions, so the new tab isn't blocked as a popup). In grid rows `MenuPdf.soloIcona` has a fixed width (`w-[4.5rem]`, icon + Aura submenu arrow): the "Azioni" auto width is computed before the MenuBar draws its button, so without it the column cuts the last buttons. Permissions are checked in `DocumentiService.documentoPer` (`ricevutaPer`, `confermaPer`): admin/segreteria see every document, a genitore only their children's, an allievo without genitore their own; anything else gets a 404. The payments list (one row per participant: quota, pagato, residuo, stato; filters; totals of the filtered rows) is `views/ElencoPagamenti`, shared by `admin/GestionePagamentiView` (admin/segreteria, edit actions) and `genitore/PagamentiFigliView` (read-only, children only); rows come from `PagamentoService.righePagamenti()` / `righePagamentiDeiFigli(username)`. The rate form is `QuotaPagamentiDialog.apriPagamento(...)`. The custom quota's "Motivo" (`Iscrizione.notaQuota`) is a ComboBox with custom values that suggests the reasons already used in every course (`PagamentoService.motiviQuota()`: no duplicates by case/spaces, most used first); no separate table.
- Reimbursements to teachers: `Rimborso` (insegnante, data, `mese` stored as the first day of the month, importo, metodo, nota) via `RimborsoService`. School year = reference months from September to August (`RimborsoService.inizioAnno/fineAnno`). `admin/RimborsiView` ("Rimborsi", admin/segreteria; delete admin-only) has one row per teacher, plus `RimborsiDialog` (the amount offered by default is the cost of the month's completed lessons not yet reimbursed) and `BilancioDialog`. `insegnante/MieiRimborsiView` is read-only. Calculations live in `BilancioService`: lessons are individual, so lesson minutes = attendances (enrolled students, absent ones included) × `Corso.durataLezioneMinuti`, and cost = minutes × current `tariffaOraria` / 60, rounded on the total. Lessons not held cost nothing. Maturato = completed lessons; costo previsto = all lessons except those not held. `Insegnante.rimborsoForfettario` ("Rimborso forfettario annuo", optional, set by admin/segreteria, read-only in the teacher's Profilo) is added to the lesson cost in every school year where the teacher has courses, fully earned from the start of the year (prospetto, `Bilancio.forfait`, costo maturato/previsto); it is not in the monthly `propostaRimborso` nor in `costiPrevistiPerCorso`.
- Documents and email: FreeMarker templates in `src/main/resources/templates` (`documenti/` for the A4 page, which must be well-formed XHTML; `email/` for the bodies). The confirmation's "Lezioni, assenze e recuperi" rules are written once in `templates/regole-corso.ftlh` (macro `regole`, `email=true` for inline styles) and used by both the email and the PDF. `DocumentiService` renders them, with values pre-formatted through `Formati`, and turns the same HTML into a PDF with OpenHTMLtoPDF (`io.github.openhtmltopdf`), so the email, the attachment and the web download always match. `EmailService` sends a confirmation of enrolment, a receipt or the yearly riepilogo (`inviaRiepilogo`/`anteprimaRiepilogo`, template `email/riepilogo.ftlh`, to the genitore or the allievo without genitore) with the PDF attached. Recipient of the enrolment documents: the genitore, or the allievo if there's no genitore with an email (`EmailService.destinatarioDi`). Only admin/segreteria can send; a receipt only when there are payments. Every attempt is stored in `InvioEmail` (metadata only; corso and allievo kept as id + name, no FK; a riepilogo has `genitoreId`/`allievoId` + `anno`; `tipo` is a `TipoDocumento` stored as VARCHAR, not a MySQL enum, after `docs/migrazioni/2026-10-23-invii-riepilogo.sql`). SMTP comes from `app.mail.*` (env vars `MAIL_*`): `MailConfig` creates the `JavaMailSender` only when the host is set, otherwise sending is simulated. Don't use `spring.mail.*`. Association data for the documents: `app.associazione.*`. UI: every document is generated, previewed and sent only from `views/DocumentiView` ("Documenti", route `documenti`; no PDF or email buttons in the other views). Admin/segreteria choose the type (`SegmentedControl`: Conferme, Ricevute, Riepiloghi) with year, course and quick-search filters; rows come from `ElencoDocumentiService` (`documentiIscrizioni(tipo)`: every enrolment for confirmations, only enrolments with payments for receipts; `riepiloghi()`: one per genitore, or allievo without genitore, and school year) with recipient, "Ultimo invio" (last non-error `InvioEmail`) and the missing-data badge; actions: PDF (`MenuPdf`) and "Invia per email" → `admin/InvioEmailDialog.apri(tipo, corso, allievo, …)` / `apriRiepilogo(genitore, allievo, anno, …)` (recipient, Anteprima, Invia); with a course chosen, "Invia conferme di iscrizione a tutti" → `InvioEmailDialog.inviaConferme` (lists who receives it and who is skipped via `EmailService.destinatariConferme`). Genitori and allievi without genitore see `ElencoDocumentiService.documentiDi(username)` (riepilogo per year, then confirmation and receipt — if paid — of every course, also past ones), PDF only; the menu item is hidden by `MainLayout` from an allievo with genitore (their documents belong to the genitore). Also `admin/GrigliaInvii`, `admin/EmailInviateView` (type filter from `TipoDocumento.getPlurale()`). Every send has an "Anteprima" button: `EmailService.anteprima(...)` builds recipient, subject, body and PDF with the same checks as `invia` (shared `verificaInviabile`/`oggetto`) without sending or recording; the body is shown in an `IFrame` with `setSrcdoc` and an empty sandbox. Test email (admin only): `admin/EmailDiTestDialog` from "Email inviate" → `EmailService.inviaTest` sends to any address the plain test message or a template filled with fictitious data (`DocumentiService.ricevutaEsempio()`, never saved) with its PDF, subject `[TEST]`, not recorded in `InvioEmail`; the dialog shows the SMTP config (no password) and the full error. `InvioEmailDialog` gets its service from `VaadinService.getCurrent().getInstantiator().getOrCreate(...)`, so it doesn't have to be passed to every dialog.
- Enrolment summary: `admin/RiepilogoIscrittiView` ("Riepilogo Iscritti", admin/segreteria, read-only) is a `TreeGrid` with one grouping level: a course row (`PagamentoService.iscrittiPerCorso()` → `IscrittiCorso` with iscritti count, quota/pagato/residuo totals, saldati) and its participants below; filters course status + school year, "Espandi tutti / Comprimi tutti", grand total in the footer (on mobile in the card column footer). Courses with groups get a second level, course → groups (`IscrittiCorso.gruppi`, plus "Senza gruppo (tutti i giorni)" when someone has none) → participants; group rows (`Voce.isGruppo()`) show only name and number of participants, and "Espandi tutti" uses `expandRecursively(..., 1)`. The course row's "Giorni / Gruppo" shows the number of groups ("sab · 2 gruppi"); Gestione Corsi has a "Gruppi" column (`CorsoService.numeroGruppi()`). Course rows have part name `riga-corso`, group rows `riga-gruppo` (styles.css). Preventive budget on the course row: "Costo insegnante" from `BilancioService.costiPrevistiPerCorso()` (same "costo previsto" as the teacher's Bilancio, summed over the course teachers with a tariff; courses without one show "Senza tariffa" and are left out of the cost/margin totals) and "Margine previsto" = Da pagare − costo. Use a `TreeGrid` like this when a list needs row grouping (the plain Grid only groups columns). On mobile `CardMobile.classi(...)` indents the child cards (a `w-…` class replaces the default `w-full`) and the course card has a "Mostra/Nascondi iscritti" button; `azioni(...)` may return null.
- Family summary (riepilogo famiglia): PDF per genitore and school year (`templates/documenti/riepilogo-famiglia.ftlh`) with the children's courses of that year (active or not), quota/pagato/residuo, subtotal per child and family totals. Data from `PagamentoService.anniDellaFamiglia` / `riepilogoFamiglia(genitoreId, anno)` (`anno` null = courses without a school year), PDF and permissions in `DocumentiService.riepilogoFamigliaPer` (admin/segreteria every family, a genitore only their own; `riepilogoPdf` without checks for the email attachment). UI: Documenti (PDF for staff and families, email from staff).
- `Corso.prezzoPreiscrizione`: optional pre-registration price, set by hand (help text shows the typical 15% discount), between 0 and `costoTotale` (checked in `CorsoService.save`). It is informational only and never changes the amount due: apply it through the custom quota. Allievi and genitori see "Prezzo di listino", "Pre-iscrizione" and "Quota dovuta" (highlighted, with a "Sconto -X €" badge) in their course lists (`views/PrezziCorso`). Confirmation and receipt (email and PDF) show the amounts through the shared macro `templates/importi.ftlh` (model `importi` from `DocumentiService`): with a custom quota the struck-through list price, the discount line with the reason (`notaQuota`, or "pre-iscrizione") and QUOTA DOVUTA / DA PAGARE highlighted. PDFs have no bold (built-in font): highlight with size/background; use "-" not the typographic minus (missing glyph).
- Inactive courses (`Corso.attivo=false`): no participant/schedule/lesson/attendance changes (checked in services), hidden to insegnante and allievo.
- School years: `AnnoScolastico` entity (table `anni_scolastici`, unique `nome` "AAAA/AAAA" with consecutive years, `attivo`), managed in `admin/AnniScolasticiView` (admin/segreteria; delete admin-only and only if no course uses it) via `AnnoScolasticoService`. `Corso.annoScolastico` stores the name as a plain string (no FK, no rename). The course dialog offers `scelteCorso(valoreAttuale)` (active years + the course's own). `AnniScolasticiIniziali` seeds the table at startup, in every profile, when it is empty.
- "I miei allievi" (`insegnante/MieiAllieviView`, INSEGNANTE only, read-only): one row per allievo and course of the teacher's active courses (titolare or secondo) from `MieiAllieviService.allieviDellInsegnante` (course name, then `Iscrizione.ORDINE`), with giorni/gruppo, orario and the `service/ConteggioLezioni` of the student: svolte = completed lessons (present or absent, `ConteggioLezioni.svolta`), da fare = `isDaFare()`, mancanti = `numeroLezioni` − svolte (never below 0), presences/absences only on svolte, lessons not held don't count. Course filter only with more than one course, `RicercaRapida`. A row click or the `BOOK` button opens `PresenzeAllievoDialog` (`lezioniDellAllievo` checks the user is a teacher of the active course; a click on the button also reaches the row, so the view ignores a second open while the dialog is open). `PresenzeAllievoDialog` (also I Miei Corsi, I Miei Figli) shows the same `ConteggioLezioni` on top, "Da fare" for lessons not completed (attendances are created as PRESENTE) and, with `noteStaff`, the "Note per lo staff" column.
- "Le Mie Lezioni" shows a badge next to the date from `views/insegnante/QuandoLezione`: Oggi, Questa settimana, Settimana prossima, plus Settimana scorsa and In ritardo for lessons not yet completed. Weeks run Monday to Sunday.
- Lessons (`Lezione`) are generated on demand with `CorsoService.generaLezioni` ("Genera Lezioni" button), not on save. Regenerating rebuilds only the scheduled lessons still to do: completed, `nonEffettuata` and `aggiunta` lessons are kept (they count for whoever attends that day), and their dates and numbers are not created again. `Corso.numeroLezioni` is the number of lessons **per participant**: a date becomes a lesson only if someone attending that weekday still needs lessons, with attendances only for them (if everyone attends every day this is the classic N dates for all; without participants N dates). `Corso.cadenzaSettimane` (column `cadenza_settimane`, null = 1; only 1 or 2, "Ogni settimana" / "Ogni 2 settimane" in the course dialog, shown in the Gestione Corsi "Giorni" column via `Formati.giorniECadenza`): every course day has a lesson every N weeks starting from its first occurrence on/after `dataInizio`; a holiday moves that lesson to the following week and the rhythm restarts from there.
- Lesson numbers in courses with groups are per weekday (Mon 1..30, Fri 1..30; make-ups take the missed lesson's number), recalculated from the lessons by date by `NumerazioneLezioni.rinumera` after generation, added/deleted lessons, group changes (back to a single counter when the last group is deleted) and at startup (`NumerazioneIniziale`, after `GruppiIniziali`); courses without groups keep the single counter. Lists show them with `Formati.numeroLezione` ("5 · Piccoli" / "5 · lun").
- Course groups: `GruppoCorso` (table `corso_gruppi`: one course day, reference time, optional name; shown by `Formati.gruppo` as "Martedì 17:00" or "Principianti – mar 17:00"). A participant belongs to at most one group (`Iscrizione.gruppo`, null = every course day) and then attends only that day. Groups are managed in `PartecipantiDialog` (section "Gruppi" + `GruppoDialog`, admin/segreteria; delete admin-only, members go back to no group) and assigned in its "Gruppo" column (shown only when the course has groups) through `CorsoService.salvaGruppo` / `eliminaGruppo` / `assegnaGruppo` (an assigned participant without a time gets the group's time; attendances of lessons still to do are synced by `sincronizzaPresenze`). A course day used by a group can't be removed from the course. Use `Iscrizione.giorniEffettivi()` / `frequenta(data)` whenever attendances are created (enrolment, generation, added lesson: a make-up goes to who had the missed lesson, a date off the course days to everyone; restored lesson). `Corso.giorniSettimana` is EAGER. The group is shown in Gestisci Presenze (`LezioneService.gruppiDeiPartecipanti`, also to teachers), Riepilogo Iscritti ("Giorni / Gruppo"), I Miei Corsi / I Miei Figli (`CorsoService.gruppiDellAllievo` + `Formati.gruppoOGiorni`) and the confirmation ("con lezione il sabato alle 10:00"). The per-participant days of the previous version (table `iscrizione_giorni`, left in MySQL by `ddl-auto=update`) are converted once at startup by `GruppiIniziali` (`CorsoService.convertiGiorniInGruppi`: one day → that day's group, otherwise no group), then the table is emptied.

## Requests source: `docs/RICHIESTE.md`

`docs/RICHIESTE.md` is the source of the user's requests (Italian). It is organized by date (`## RICHIESTE del GG-MM-AAAA`) and by scope (`### AMBITO`), each request being a checkbox item `* [ ] …`.

- **Reference**: each item is identified as `[AAAA-MM-GG/AMBITO.n]`, where `AMBITO` is a short upper-case key of the section: its title, or its main word for long titles (`### CORSI` → `CORSI`, `### DASHBOARD INIZIALE` → `DASHBOARD`, `### Docenti diventano Insegnanti` → `INSEGNANTI`) and `n` is the 1-based position of the item in that section, e.g. `[2026-10-10/LOGO.2]`. Don't renumber or reorder items written by the user.
- **Implementation session** — whenever the user asks to implement the requests (all open items `[ ]`, a date, or a scope), always follow these phases in order:
  1. **Read-only analysis**: read the open items, the code they touch and the Vaadin docs (MCP) needed. No file changes yet.
  2. **Clarification round — mandatory, before writing the plan.** Ask *all* the questions needed to make every open item explicit, with `AskUserQuestion` (up to 4 questions per call, several calls if needed; concrete options with the recommended one first and a short description of the consequences). Don't fill gaps with silent assumptions and don't postpone questions to the execution. Always ask about:
     - incomplete or contradictory items (e.g. a truncated sentence) and terms that can be read in more than one way;
     - who: which roles see/do what, including roles the item doesn't mention but are affected (e.g. a new view: who else can access it? may they delete?);
     - where and how in the UI: which view, dialog or menu entry; new view vs extension of an existing one; behaviour on mobile;
     - data: new fields and whether they are mandatory, defaults, effect on existing data and on production (schema changes, renames, migrations);
     - side effects and edge cases (e.g. what happens to related records when something is added/removed);
     - anything not requested that you would add or change "by the way" (validation, refactoring): propose it, don't just do it.
     Skip a question only when the answer is unambiguous from the item text or from the code. When the round is over, write a short summary of the decisions.
  3. **Record the answers**: in the plan (*Analisi*, sub-section **Decisioni**, one line per decision with the item reference) and, in the same plan commit, under the item in `docs/RICHIESTE.md` as an indented line `_Chiarimento AAAA-MM-GG: …_` (never rewrite the user's text). Items the user chooses to leave open get `_(da specificare: …)_` and go in *Fuori ambito*.
  4. **Plan and execution, without further approval**: follow the workflow below as already defined — plan in `docs/piani/` committed alone (each step names the request(s) it completes, column *Richiesta*), then one step at a time: implement, verify, mark the step in the plan, mark the request in `docs/RICHIESTE.md` when the step completes it, commit; new work goes in the plan as new steps; close with the *Registro*.
  5. **Questions during execution**: if a new ambiguity appears, ask immediately when the decision is the user's (behaviour, data, production, scope) and record the answer as in phase 3 (commit the plan/RICHIESTE update before continuing); purely technical choices are decided and noted in the plan.
- **Completion**: the commit that completes an item also marks it in `docs/RICHIESTE.md` as `* [x] … _(completata AAAA-MM-GG)_` and has the reference in the subject: `<step id> [AAAA-MM-GG/AMBITO.n] <short description in Italian>`, e.g. `3 [2026-10-10/LOGO.2] Logo in fondo al menu laterale`. One commit per completed request; if a step completes several closely tied items, list all references (`[2026-10-10/LOGO.1][2026-10-10/LOGO.3]`). Preparatory steps that complete no item use the normal subject. An item found already implemented is marked with a note (`_(già presente, verificata AAAA-MM-GG)_`) in its own commit.
- Never mark an item completed if it is only partially done: leave `[ ]` and add a short note under it.

## Feature requests from prompts: `docs/FUNZIONALITA.md`

When a prompt asks for a new feature or a change to the application's behaviour, UI or data (not for questions, reviews, bug fixes or changes to tooling/configuration/docs, which follow the normal workflow), first record it, then process it. A `UserPromptSubmit` hook in `.claude/settings.json` reminds you of this on every prompt; when in doubt whether a prompt is a feature request, ask.

1. **Record**: add the request to `docs/FUNZIONALITA.md`, same format as `RICHIESTE.md`: section `## FUNZIONALITA del GG-MM-AAAA` (today, created if missing), scope `### AMBITO` (reuse an existing scope of that date when it fits), one `* [ ] …` item per distinct request, with the user's words reported faithfully (split a multi-request prompt into items, don't rephrase or add interpretations). Reference: `[F-AAAA-MM-GG/AMBITO.n]` (the `F-` prefix distinguishes it from `RICHIESTE.md` items). Commit the file alone: `Funzionalità: <short description>`.
2. **Process**: immediately run the *implementation session* described above on the new items, with `docs/FUNZIONALITA.md` in place of `docs/RICHIESTE.md` for clarifications (`_Chiarimento …_`), completion marks and commit references (e.g. `2 [F-2026-10-11/CORSI.1] …`).

## Workflow: plan first, then execute with one commit per step

Every user request that changes the repository (code, configuration, build, docs) follows this workflow — no exceptions for "small" changes. Pure questions, explanations or reviews without changes don't need a plan.

### 1. Plan first

For `docs/RICHIESTE.md` implementation sessions the mandatory clarification round (see *Requests source*) comes before this step.

Before touching any code, write the plan to a new file `docs/piani/AAAA-MM-GG-<argomento>.md` (Italian, e.g. `docs/piani/2026-10-07-responsive-mobile.md`). Analysis and read-only checks (reading code, Vaadin MCP docs, running the app) can happen before writing it, to make the plan accurate.

The plan contains:
- **Richiesta**: the user's request, in one or two sentences.
- **Analisi**: what was found (problems, constraints, references to docs/APIs checked).
- **Passi**: a table of numbered steps (`1`, `2`, … or `1.1`, `1.2` if grouped in phases) with columns *Passo · Cosa · File · Verifica · Stato* (`[ ]`, `[x]`, `[~]`). Each step must be small enough to be one coherent commit.
- **Fuori ambito**: what is deliberately not done, and open decisions.
- **Registro**: filled in during execution (outcome, test results, problems found).

Commit the plan alone as the first commit: `Piano: <argomento>`. Then show the user a short summary of the steps and **proceed with the execution without waiting for approval**, unless the plan contains a decision that is genuinely the user's (e.g. version numbers, deleting data, changing production behaviour): in that case ask first.

Existing plan `docs/PIANO-CORREZIONI.md` stays as the reference for the architecture review; new requests get their own file in `docs/piani/`.

### 2. Execute: one commit per step

Commit after **every single step** of the plan, not at the end of a phase or of the whole plan. The user has authorized these commits in advance; push is still only on explicit request.

For each step:
1. Implement only that step.
2. Verify it: at least `./mvnw -q compile`; run `./mvnw test` when the step touches services, repositories, views or tests. Do not commit a step that doesn't compile or breaks tests — fix it first.
3. In the same commit, mark the step `[x]` in the plan (or `[~]` with a short note if partial/deferred).
4. Stage only the files of that step (`git add <files>`, never `git add -A` with unrelated changes) and commit on the current branch (`develop`), not on `main`.
5. Commit message: `<step id> <short description in Italian>` as subject, e.g. `1.5 CorsiView: Binder locale al dialog`, with a body explaining what changed and why if not obvious.

If a step turns out to be already done or unnecessary, mark it in the plan with a note and commit just the plan update. If new work emerges during execution, add it to the plan as new steps (committing the plan change) rather than doing it silently. Pre-existing uncommitted changes of the user go in a separate commit, never mixed into a step.

### 3. Close

Last commit: fill in the **Registro** of the plan with the final verification (build, tests, browser checks) and anything left open. Then report to the user with the list of commits.
